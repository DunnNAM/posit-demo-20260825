# Decision Register — CAQ Posit Connect Cloud Demonstrator

Every decision that constrains scope, data or code. Referenced inline in code comments as
`D-###`. ID scheme inherited from the existing MDT dashboard prototype.

**Status key:** `Agreed` · `Proposed` (awaiting sign-off) · `Superseded`

---

## Scope and framing

### D-001 — Synthetic data only, seeded and committed
**Status:** Agreed · **Date:** 2026-08-19
All data is generated by `data-raw/generate_synthetic_data.R` with a fixed random seed and
committed to the repository. No real, derived or re-identifiable data enters the project at
any point.
**Rationale:** The repository is public and Connect Cloud is public-internet hosted.
**Consequence:** Regeneration is reproducible; the generator script is itself a demo asset.

### D-002 — No claim of clinical validity
**Status:** Agreed · **Date:** 2026-08-19
Indicator definitions are plausible, not endorsed. The report and app carry a visible
synthetic-data statement on the landing view.
**Rationale:** Without it, Clinical leads A and B will spend the demo debating case
ascertainment instead of watching the publishing workflow.

### D-003 — No live database connection
**Status:** Agreed · **Date:** 2026-08-19
Data ships as flat files in the repository. No `DBI`/`odbc` code path, unlike the existing
prototype's `USE_REAL_DATA` flag.
**Rationale:** MSSQL/SSIS integration is a conversation for Tech lead 1, not a build item
for a 5-day demo.

### D-004 — Persona switching via dropdown, not Connect identity
**Status:** Agreed · **Date:** 2026-08-19
Role-based content is demonstrated with a visible "View as" selector. Real
`session$user` / `session$groups` authorisation is **not** implemented.
**Rationale:** Real group-based auth needs accounts provisioned in Connect Cloud and
tested under load — the highest-risk item available, on the shortest timeline available.
**Consequence:** The data model is unaffected — it still carries a facility key and a
persona-to-scope mapping — so this can be swapped to real identity later without a data
change. Narrate the swap explicitly during the demo.

### D-021 — Reusable template packaging is out of scope
**Status:** Agreed · **Date:** 2026-08-19
Not a template project. Components may be harvested afterwards for reuse.
**Consequence:** Comment for transferability, but do not invest in generalisation,
parameterisation or packaging.

## Indicators and data model

### D-005 — Six indicators; four core, two build-if-time
**Status:** Agreed · **Date:** 2026-08-19
Core: surgery rate, time to surgery, hospital-acquired complications, prolonged LOS.
Build-if-time: 28-day readmission, stage at diagnosis distribution.
**Rationale:** The two additions unlock funnel plots with meaningful small denominators
(readmission) and the explanatory drill-down for signal S2 (stage). Generation cost is
negligible; the cost is report and app real estate.

### D-006 — One row per patient, pre-calculated results
**Status:** Agreed · **Date:** 2026-08-19
One diagnosis per patient. Indicator outcomes are stored as binary flags or numeric
columns, not derived from an underlying episode structure.
**Rationale:** CAQ already has robust pipelines handling the real complexity. This project
demonstrates Posit capabilities, not data modelling.
**Consequence:** Cannot represent multiple primaries or multiple treatment episodes. Do
not extend without revisiting this decision.

### D-007 — Eligibility expressed as `NA`
**Status:** Agreed · **Date:** 2026-08-19
Patients not eligible for an indicator carry `NA` in that indicator's result column.
Denominator membership is `!is.na(result_col)` for surgical-cohort indicators, and the full
cohort for all-diagnosed indicators, as declared by `indicator_definitions.csv`.
**Rationale:** Simpler than parallel `elig_*` flag columns, and `NA` is self-documenting.
**Consequence:** All summarisation must use explicit `na.rm` handling with denominators
counted from non-`NA` rows — never `mean(x, na.rm = TRUE)` without confirming the
denominator is the intended one.

### D-008 — Metadata-driven stratification menu
**Status:** Agreed · **Date:** 2026-08-19
`indicator_definitions.csv` declares `cohort` and `facility_dims_allowed`. The Shiny app
constructs its group-by and filter choices from that table at runtime.
**Rationale:** Patients are attached to a facility only if they had surgery, so surgery rate
and stage distribution cannot be analysed by facility. Enforcing this in metadata makes the
invalid option unrenderable rather than merely discouraged.
**Consequence:** Adding an indicator means adding a row to the CSV, not editing UI code —
a governance talking point for Tech lead 1.

### D-009 — "Time to first treatment" renamed "Time to surgery"
**Status:** Agreed · **Date:** 2026-08-19 · **Supersedes:** initial indicator list
Measured diagnosis → surgery, surgical cohort only.
**Rationale:** Under D-006, facility is only assigned to surgical patients, so
"first treatment" would not be facility-attributable for patients whose first treatment was
systemic therapy or radiotherapy. Renaming keeps three facility-level indicators, which is
what makes a facility-level report worth writing.

### D-010 — Star-ish schema, five CSVs
**Status:** Agreed · **Date:** 2026-08-19
`patients` (fact) + `facilities`, `hhs`, `indicator_definitions`, `user_roles`
(dimension/metadata). Joined once in `R/data_prep.R` into a single analysis-ready tibble
consumed by both products.
**Rationale:** Looks like a warehouse to Tech lead 1; gives a defensible single source of
truth; keeps the app fast by joining once at startup rather than reactively.

### D-019 — Stratifier list fixed; First Nations and remoteness excluded
**Status:** Agreed · **Date:** 2026-08-19
Available: age group (5-yr, 10-yr), sex, HHS of residence, treatment facility, HHS of
treatment facility, diagnosis year, stage, SEIFA quintile, tumour stream.
**Rationale for exclusion:** Both are realistic and CAQ-relevant, but a synthetic disparity
appearing on screen in front of this audience invites a response to a finding that does not
exist. SEIFA is retained as it carries lower reactive risk and still demonstrates
socioeconomic stratification.

### D-020 — Five-year period derived, not stored
**Status:** Agreed · **Date:** 2026-08-19
`diagnosis_period` (2015–19 / 2020–24) is computed in `R/data_prep.R`.
**Rationale:** If the report and app ever disagree on the period cut in front of this
audience, the demo is over.

### D-011 — Planted signals, documented
**Status:** Agreed (S1, S2, S3) · **Date:** 2026-08-19
- **S1** — Colorectal, one facility, prolonged LOS: baseline 2015–17, progressive
  deterioration 2018–2023, sharp correction 2024.
- **S2** — Lung, two HHSs of residence, surgery rate materially lower.
- **S3** — Lung, same two HHSs, stage skewed later. **Sized so stage explains approximately
  half the S2 gap**, leaving a service-access residual.

**S3 generator consequence:** introduces a dependency chain — stage is conditioned on
residence HHS (lung only), and surgery probability is conditioned on stage. The generator
must therefore draw stage before surgery, and the validation block must confirm the
stage-adjusted gap is roughly half the crude gap.

**Rationale:** Without planted signal every chart is noise and the demo is boring. S1 is
specifically shaped so that the 2015–19 vs 2020–24 aggregation under-calls it — the static
report shows a mild deterioration, the app shows the rise, peak and recovery. That contrast
is the core argument for the dashboard.
**Consequence:** Recorded here so no reader mistakes a designed artefact for a finding.

### D-012 — Suppression at n < 5, with a user-adjustable volume threshold
**Status:** Agreed · **Date:** 2026-08-19
Cells with counts below 5 are suppressed. The app additionally offers a "hide facilities
with fewer than *x* cases" control, defaulting to 5.
**Rationale:** CAQ staff will look for suppression; its absence is more noticeable than its
presence. Kept deliberately light — one or two visible examples is sufficient.
**Consequence:** Implemented once in `R/suppression.R`, not per chart.

## Technical and environment

### D-018 — `renv` adopted for local reproducibility; `manifest.json` is the deployment artefact
**Status:** Agreed, **revised 2026-08-19** following Day 1 deployment evidence
`renv.lock` is committed at the repository root. **Connect Cloud does not activate renv** —
the Day 1 build log states that renv environments are not activated and that
`renv/activate.R` is truncated to prevent accidental use. Dependencies are collected from
`manifest.json` instead.

**Rationale for retaining `renv` regardless:** it provides the reproducible local environment,
aligns with the CAQ move to Posit Team, and is the source `rsconnect::writeManifest()` reads
when pinning package versions into the manifest. Version pinning does travel to Connect
Cloud — via the manifest rather than the lockfile.

**Presentation consequence — important.** Do not claim that Connect Cloud restores
`renv.lock`. It does not. The accurate narration is that `renv` pins the environment locally,
`writeManifest()` transfers those pins into `manifest.json`, and Connect Cloud provisions
from that. Tech lead 2 is likely to know the difference.

**Performance note:** Connect Cloud reported it *provided* all 94 packages rather than
installing them, in roughly two seconds. Packages are pre-built and cached server-side.

### D-015 — Explicit `library()` calls, not `pacman::p_load()`
**Status:** Agreed · **Date:** 2026-08-19 · **Departs from:** existing prototype `global.R`
**Rationale:** `renv::snapshot()` discovers dependencies by static analysis of `library()`,
`require()` and `::` calls. Package names passed as bare symbols to `pacman::p_load()` are
invisible to it, producing an incomplete lockfile and a failed restore on deployment.
**Consequence:** `pacman` is not used in this project. Package list is visible at the top of
`app.R` and the `.qmd` setup chunk — which also reads better to Tech lead 2.

### D-016 — All function calls namespaced
**Status:** Agreed · **Date:** 2026-08-19
`ggplot2::geom_line()`, `dplyr::filter()`, and so on throughout.
**Rationale:** Standing CAQ convention; supports transferability between staff.
**Exception:** the `%>%`/`|>` pipe, and `ggplot2` layer composition with `+`.

### D-013 — Adopt a subset of the existing prototype's UI layer
**Status:** Agreed · **Date:** 2026-08-19
**Adopt:** `R/theme.R` verbatim (CAQ palette, `scale_colour_caq()`, `scale_fill_caq()`,
`theme_set()`); the `bslib::bs_theme()` block; the `.card`, `.card-header` and `.kpi-box`
CSS rules.
**Do not adopt:** filter rail, overlay drawer, chip strip, `drawer.js`, and the remaining
~670 lines of `style.css`. Use stock `bslib::page_sidebar()` for filtering.
**Rationale:** The prototype's custom chrome is substantial and would consume the time
budgeted for the persona switcher. Stock `bslib` cannot break in ways that are hard to
diagnose live.
**Consequence:** Less visual polish than the MDT prototype. Revisit only if Day 4 finishes early.

### D-014 — `plotly` for funnel plots only
**Status:** Agreed · **Date:** 2026-08-19
Funnel plots use `plotly::ggplotly()` for tooltips and series toggling, consistent with
current CAQ practice. All other plots are static `ggplot2`.
**Rationale:** Funnel plots are unusable without tooltips — points are unidentifiable
otherwise. Elsewhere, interactivity comes from inputs and `plotly` only adds failure modes.
**Consequence:** `ggplotly()` drops `subtitle` and `caption` from `ggplot` objects, so
suppression footnotes on funnel plots must be rendered as separate UI text (see I-004).

### D-017 — Repository layout: full clone, single root manifest, shared layer at root
**Status:** **RESOLVED 2026-08-19** by Day 1 deployment evidence · **Supersedes** the original
flat-root decision and the Option A/B/C choice raised earlier the same day.

**Confirmed layout:**
```
/app.R                        Shiny entry point
/manifest.json                SINGLE manifest, union of packages
/R/                           Shared layer — one canonical copy
/data/                        Committed synthetic CSVs
/report/facility-report.qmd   Quarto entry point
```

**Evidence.** Connect Cloud performs a full `git clone` of the repository into
`/cloud/project` and sets that as the working directory. The manifest's file list does not
filter the bundle — the report deployed from `report/` successfully reached `R/` and `data/`
at the root. The build log further showed that a manifest in the content's own subdirectory
was **ignored**: Connect Cloud read the root manifest (94 packages, `appmode: shiny`) and took
the content type from the publish request instead, noting the mismatch and proceeding.

**Consequences:**
1. One `manifest.json` at the root, carrying the union of both content items' packages.
   `report/manifest.json` is redundant and should be deleted.
2. Content type is selected per publish request in the Connect Cloud interface, not by the
   manifest.
3. The shared `R/` layer exists in exactly one place. **No build script, no duplicated files,
   no staleness risk** — I-011 remains closed, which the earlier Option A proposal would have
   reopened.
4. `manifest.json` must be regenerated when the file list or package set changes (I-015).

### D-022 — Drop `showtext`; fonts handled per-product
**Status:** Agreed · **Date:** 2026-08-19 · **Departs from:** existing prototype `global.R`
`showtext` and `sysfonts::font_add_google()` are not used. The Shiny app uses
`bslib::font_google("Lato")` via the theme; the Quarto report uses a system sans-serif.
**Rationale:** `showtext` fetches fonts over the network at render time and interacts with
DPI in ways that silently change text sizing between local RStudio and a deployed render.
The visual cost of dropping it is minor; a broken render on demo day is not.
**Consequence:** the `bslib::font_google()` path is still a network dependency at build time
and is explicitly exercised by the Day 1 deployment probe (I-003).

### D-023 — Suppression order: aggregate, then suppress the label
**Status:** Agreed · **Date:** 2026-08-19
Aggregation runs across all facilities. Facilities below the threshold **retain their point**
on funnel plots but have their identifying label suppressed. Suppression never removes a
facility before the pooled mean and control limits are computed.
**Rationale:** funnel plots derive their value from low-volume facilities — that is what the
widening control limits illustrate. Suppressing them before aggregation would both empty the
informative region of the plot and shift the pooled mean.
**Consequence:** tabular output suppresses the count; the funnel plot suppresses the label.
Two different behaviours from one rule, and both must be captioned.

### D-024 — Day 1 probe content items become the real content items
**Status:** Agreed · **Date:** 2026-08-19
The Day 1 deployment probe is published as `app.R` and `facility-report.qmd` — the same
filenames the finished products will use. Real content replaces the placeholder content in
place; the files are never renamed.
**Rationale:** Connect Cloud deployment records are bound to a repository and primary file.
Keeping the filenames stable means Day 1's deployment configuration is never thrown away,
every subsequent push updates an already-working content item, and the push-to-redeploy
demonstration runs against something that has been deploying successfully all week.

### D-025 — `R/` is auto-sourced by Shiny; the dependency declaration lives at the root
**Status:** Agreed · **Date:** 2026-08-19 · **Arises from:** I-013

Shiny automatically sources every `.R` file in an `R/` directory adjacent to `app.R`.
Consequences adopted as project conventions:

1. **`dependencies.R` sits at the repository root, not in `R/`.** It is a declaration file
   that must never execute. `renv` scans all `.R` files in the project regardless of
   location, so detection is unaffected.
2. **Every file in `R/` must be safe to source on app startup** — function definitions and
   constants only, no side effects beyond `ggplot2::theme_set()` in `theme.R`.
3. **Shiny modules go in `R/` and need no manual source list.** This removes the
   hand-maintained `source()` block that the earlier MDT prototype carries at the foot of its
   `global.R`, and with it the risk of a module being added but not sourced.
4. **The Quarto report does not get this behaviour** and retains an explicit
   `source("R/...")` call in its setup chunk.

**Rationale:** discovered empirically on Day 1 — `lubridate` and `plotly` attached during a
local app run despite `app.R` not calling `library()` for either.

### D-026 — Render via the Quarto CLI; the `quarto` R package is not a dependency
**Status:** Agreed · **Date:** 2026-08-19

The report is rendered with the Quarto CLI — RStudio's Render button locally, and Connect
Cloud's build host on deployment. The `quarto` R package is deliberately **not** added to
`dependencies.R` or `renv.lock`.

**Rationale:** the package is only a wrapper for invoking the CLI from an R session. Connect
Cloud never calls it. Including it would add a dependency that serves local convenience only,
against a project that is actively measuring restore time (I-001, check 2). `knitr` and
`rmarkdown` remain declared — those are what the CLI actually needs to execute R chunks.

**Consequence:** do not call `quarto::quarto_render()` in project code or documentation. Use
the Render button, or `quarto render facility-report.qmd` from a terminal.

### D-027 — Deploy source via the Git-backed flow, never pre-rendered output
**Status:** Agreed · **Date:** 2026-08-19

Both content items deploy by connecting the GitHub repository to Connect Cloud and letting
Connect Cloud render the source on its own build host. Local rendering followed by a static
upload (`quarto publish`, or the IDE "finished document only" option) is **not** used.

**Rationale:** the demonstration's central claim is push-to-redeploy from Git. A pre-rendered
upload has nothing to redeploy, never restores `renv.lock`, and executes no code on the
host — which would leave I-001 checks 3 to 6 testing nothing at all. The Shiny app requires a
live server process and must deploy from source regardless, so a static report would leave
the presentation narrating two unrelated publishing mechanisms.

**Consequence:** every content update reaches Connect Cloud by commit and push. Note that the
IDE publishing dialog (rsconnect / Posit Publisher) is a different path from the Git-backed
flow and should not be used for this project.
